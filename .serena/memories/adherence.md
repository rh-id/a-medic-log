# Adherence & Dose Occurrences (issue #12 design, R1)

## Two-table model
- `medicine_dose_occurrence` = EXPECTATION snapshot only: reminder_id (indexed, deliberately NO FK so deleting a reminder preserves history), medicine_id (FK CASCADE with medicine), scheduled_date_time, created_date_time; UNIQUE(reminder_id, scheduled_date_time) + insert IGNORE = idempotent generation. NO taken/missed column — taken/missed/extra are DERIVED at report time by pairing with `medicine_intake`; never persist the pairing.
- `medicine_intake` = user's dose diary (taken_date_time, no schedule link). PRN intakes with no reminder are legal and count as extra. Do not merge the tables: expectations are system-owned/immutable-in-past, intakes are user-owned CRUD.
- Reminder delete keeps past occurrences (no FK); medicine/note/profile delete cascades occurrences + intakes together.

## MedicineRepository is the SOLE bookkeeping entry point (R1)
- `MedicineRepository` (base, app-scope singleton via DatabaseProviderModule — nested providers fall through) owns ALL occurrence writes. `DoseOccurrenceGenerator`/executor were RETIRED; the former `ReentrantLock mOccurrenceLock` was REMOVED: atomicity and cross-thread serialization are each entry point's single encompassing transaction (SQLite single writer — Room takes the writer lock at BEGIN, a concurrent transaction BLOCKS then re-reads fresh state; nested same-thread transactions coalesce into the outermost). No dedicated executor exists.
- Package-private lock-free CORES (deterministic, fixed-date testable — covered on REAL Room in androidTest): `generateFor(reminder, lower, upper)` strict `lower < scheduled <= upper`, Calendar day-stepping (NEVER `millis += 86400000` — DST), `truncateAfter(reminderId, time)`, `routineCatchUp(reminder, ceiling)`, `initialBackfill(reminders, ceiling)`. Public entry points wrap them under the ONE-TRANSACTION INVARIANT: every occurrence-affecting entry point is EXACTLY ONE `runInTransaction` with its decision reads INSIDE it (fresh re-read, caller before-snapshots never trusted; persisted stamps copied onto the edited entity before transition-stamping). Composing two transactions or reading outside the tx before deciding is silently racy — the DB only serializes what one transaction spans.
- 2 documented rules (class javadoc): exactly one transaction per entry point; fresh re-read inside that transaction. This structural invariant IS the concurrency control (no lock).
- Entry points: insertMedicineReminder (create-stamp + generate created→endOfToday when enabled; nested call from insertMedicine — nested same-thread tx coalesces into the outermost), updateMedicineReminder, insertMedicine, updateMedicine (fresh diff via queryMedicineInfo), deleteMedicineReminder (`now` captured BEFORE the delete; delete + truncateAfter(now) one tx), catchUpEnabledRemindersByProfile / catchUpAllEnabled (reader catch-up), backfillOccurrences(now) (re-reads `findMedicineRemindersAll` itself INSIDE the tx — takes no caller-supplied list; flag stays in MedicineReminderEventHandler). Passive FK-cascade deletes (deleteMedicineByMedicineId) are documented OUTSIDE the rule: single passive DELETE, no read-decide-write.
- Stamps: `lastEnabledDateTime`/`lastDisabledDateTime` on MedicineReminder, NEVER cleared once set — they are the generation floor. `stampCreation` is public static on MedicineRepository; ImportArchiveCmd calls it as pure field mutation pre-insert, then applies the archive's real stamps (`last_enabled_date_time`/`last_disabled_date_time`, nullable → JSON null) OVER the stampCreation defaults when present — export/import round-trips the stamps; a legacy archive (older app version, no stamp keys / JSON null) keeps the stampCreation fallback. Documented exception: pure field mutation, no DB access, must stay in parity. Second known exception: NoteRepository.insertNote inserts reminders raw (always empty list today); caller exceptions are documented at their call sites, not in the repository javadoc.
- GUARANTEE: a disable→re-enable off-period is never regenerated (floor = max(latest occurrence, lastEnabled, lastDisabled, created); catch-up no-ops while disabled). History ≤ transition-time is immutable; disable/edit/delete truncate only `scheduled > now`. Write-side generation of created→endOfToday is LOAD-BEARING: pull-only generation silently loses the created-to-disabled window for reminders disabled before any read (rejected design).
- Adding a reminder write path ⇒ use a MedicineRepository entry point (never raw DAO writes on reminders/occurrences).

## Matching (AdherenceCalculator / TodayCalculator — pure JVM, unchanged by R1)
- Per medicine over the WHOLE range (NOT day-bucketed): nearest unconsumed intake within ±`WINDOW_MILLIS` (3h fixed, parameterized overload) of scheduled → TAKEN on the occurrence's day; else MISSED. Cross-midnight attribution works (23:00 dose taken 01:00 counts).
- Occurrences > now = not yet due, excluded. Unconsumed in-range intakes = EXTRA on the intake's day (PRN included); extras NEVER affect percent = taken/(taken+missed).
- Intake queries widened ±WINDOW_MILLIS on BOTH range ends; out-of-range intakes never count as extra.
- TodayCalculator groups intakes per medicine (NEVER per profile). The per-medicine unmatched groups come from a HashMap: the merged list is re-sorted `Comparator.naturalOrder()` BEFORE the missed/next-dose scan, or the first-hit highlight can pick a non-earliest dose. TODAY CARD missed semantics differ from the report: missed = unmatched AND take-window fully elapsed (`time + WINDOW_MILLIS <= now`, inclusive); a due dose whose window is still open is still takeable (hasActiveDose → card IN_PROGRESS, not missed, not nextDose); report semantics unchanged (historical windows are closed anyway). Report commands: repo catch-up first, then scoped queries (findMedicinesByProfileId JOIN; occurrences + widened intakes), pure calculator.

## Rejected alternatives (do not re-litigate without new facts)
- Event-driven (generator subscribes to *ChangeNotifier): REJECTED — nested reminder paths (New/UpdateMedicineCmd) fire NO per-reminder events (only whole-state payloads), import fires none ⇒ no structural coverage; moving stamping to a handler second write opens a crash window that regenerates the off-period; async handler ordering can insert unhealable past-dated phantoms; commands block on handler work anyway via subject drain.
- Pull-only generation (write = stamp + truncate only): REJECTED — reminders disabled before any read lose their created-to-disabled expected doses forever (catch-up no-ops when disabled).
- runInTransaction-as-mutex (no JVM lock): the occurrence lock EXISTED (ReentrantLock mOccurrenceLock) and was later REMOVED — decision final: serialization is the single encompassing transaction per entry point (SQLite single writer, writer lock at BEGIN; concurrent txs block then re-read fresh state; reviewer-verified for both journal modes). What remains binding is the structural one-transaction invariant: two composed transactions or a decision read outside the tx would be silently racy.
- Known deferred follow-ups: AppNotificationHandler.disableMedicineReminder holds mLock + blockingGet() on the shared 5-thread pool (pre-existing starvation pattern, practically unreachable single-user); historical export files lack stamps (handled: legacy fallback to stampCreation + catch-up floor at createdDateTime).
